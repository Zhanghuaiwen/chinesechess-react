# Part 1 必答 20 题（建议逐字练）

## Q1. 用一句话介绍这个项目，最核心的难点是什么？

**答**：一个“本地可下、联机可战、引擎可分析”的中国象棋平台。核心难点不是画棋盘，而是三件事同时成立：规则前后端一致、联机状态有唯一权威、引擎请求在异步环境下可控。

**追问：为什么做象棋？**
答：象棋规则边界多（马腿、象眼、炮架、飞将、困毙），能同时验证搜索算法和状态机；而且结果可现场演示，不需要外部数据。

**雷区**：不要花 2 分钟讲 UI 配色；先讲工程问题。

---

## Q2. 为什么规则要前后端共享？怎么保证不漂移？

**答**：规则只写一份在 `shared/gameLogic.js`，前端用它做交互提示（`getSafeMoves`），服务端用它做最终裁决（`Game.applyMove`）。漂移的根源是两份实现，所以从结构上消除第二份。

**机制**：

- `shared/` 零环境依赖，不碰 DOM/Node API，浏览器和 Node 都能 import；
- 前端只信“提示”，服务端永远重算，不信任客户端提交的合法性；
- 单机和联机的终局判定都走同一组函数：`hasLegalMove`、`boardKey`、`makeMove`。

**边界**：协议类型没有跨端 import，是手写对齐；这是取舍，换取前后端构建解耦。

**改进**：把协议类型也抽到 `shared/protocol.ts`，用生成器或 `zod` 做运行时校验。

---

## Q3. 联机为什么必须服务端权威？客户端乐观 UI 怎么收敛？

**答**：服务端权威解决三个问题：防作弊、防双发、防乱序。客户端只提交“走子意图”，不提交“走子结果”。

**机制**：

- 客户端点击时本地 `makeMove` 先落子，保证手感；
- 同时发 `game.move { baseSeq, from, to }`；
- 服务端校验通过后广播全量快照；
- 客户端收到快照直接覆盖本地棋盘，乐观结果被权威结果收敛。

**边界**：当前是“乐观 UI + 快照收敛”，不是严格回滚；如果服务端拒绝且没有新快照，需要 `sync.request` 主动拉取。

**改进**：保存 `optimisticBackup`，收到拒绝立即回滚，减少错误局面停留时间。

---

## Q4. 全量快照 vs 增量同步，为什么选全量？

**答**：因为棋盘很小（10×9），全量快照只有几 KB，但能把“恢复、对齐、展示、结算”四件事一次解决。

**对比**：

- 增量需要处理丢包、乱序、重放、补偿，客户端要维护“已确认到第几手”；
- 全量任意时刻收到都能直接渲染，重连不需要 replay；
- 代价是带宽略大，但在象棋场景完全可接受。

**追问：什么时候会换增量？**
答：高频状态（比如实时坐标、观战万人）或棋盘很大时才值得；象棋回合制、低频走子，全量更划算。

---

## Q5. `baseSeq` 是什么？为什么需要它？

**答**：它是客户端认为自己基于的权威版本号，服务端只在 `baseSeq === seq` 时接受走子。

**机制**：

```text
服务端 seq=7
A 基于 7 提交 → 接受，seq=8
B 仍基于 7 提交 → stale_seq 拒绝
B 收到拒绝 → sync.request → 收 seq=8 快照 → 对齐
```

**为什么不是锁**：象棋是回合制，真正并发写入很少；乐观并发失败成本低（重发一次），比维护锁状态简单。

**追问：重试会不会重复落子？**
答：不会。第一次即使成功但响应丢失，重试仍带旧 `baseSeq`，会被 `stale_seq` 拒绝；服务端不会执行两次。

---

## Q6. 断线重连怎么做？对局会暂停吗？

**答**：不暂停。服务端保留座位 30 秒，对局继续，对手可以走子；30 秒内凭 `sessionId` 恢复，超时判负。

**服务端**：

```text
close → markOffline(ws=null, offlineUntil=now+30s)
      → 广播快照（对手看到倒计时）
      → 30s 后 expireOffline：
          playing → 判对手胜
          waiting → 释放座位
```

**客户端**：

```text
sessionStorage 保存 {gameId, sessionId}
重连成功 → room.resume
退避 1/2/4/8/16 秒，最多 8 次
心跳 15 秒，40 秒无 pong 判死
```

**追问：为什么对局不暂停？**
答：暂停会被恶意利用（断网拖时间）；保留座位 + 倒计时是更常见的竞技做法。

---

## Q7. `playerId`、`sessionId`、`token` 为什么要分开？

**答**：三者生命周期和作用域不同，混在一起会互相污染。

| 标识 | 存储 | 作用 | 生命周期 |
| --- | --- | --- | --- |
| `playerId` | localStorage | 排位身份 | 跨对局 |
| `sessionId` | sessionStorage | 单局座位凭据 | 单局/单标签 |
| `token` | localStorage | 账号会话 | 30 天 |

**例子**：

- 换账号不应丢当前座位 → 座位只认 `sessionId`；
- 换设备不应继承排位 → 排位认 `playerId`/账号；
- 刷新页面不应重新登录 → 账号认 `token`。

**追问：sessionId 泄露会怎样？**
答：别人可以抢座位。当前是 UUID + 只存服务端内存，风险有限；生产应加绑定（IP/设备指纹）和一次性轮换。

## Q8. 讲一下 Minimax 和 Alpha-Beta。

**答**：Minimax 假设双方都最优：AI 层最大化、对手层最小化，递归到深度或终局，回溯选最优。Alpha-Beta 用 `[alpha, beta]` 窗口剪掉不可能影响结果的分支。

**核心代码逻辑**：

```text
if 吃到将: return ±(100000 + depth)
if 无着法: return 当前方输
if depth == 0: return evaluate(board)
for move in 吃子优先排序:
    score = minimax(..., !isMax)
    alpha/beta 更新
    if beta <= alpha: 剪枝
```

**为什么剪枝不影响正确性**：`beta <= alpha` 表示当前分支的结果不可能被上层选择；上层已有更优解，继续搜索不会改变最终 minimax 值。

**追问：为什么不用 negamax？**
答：等价，但当前评估以红为正，minimax 的 max/min 更直观；negamax 要每层翻转符号，容易在“黑方 AI”上出视角 bug。

---

## Q9. 走法排序和迭代加深做了什么？

**答**：排序按被吃棋子价值（将 6 > 车 5 > 炮 4 > 马 3 > 象 2 > 士 1 > 兵 0），吃子优先，让 alpha/beta 更快收紧。迭代加深从 depth 1 搜到 maxDepth，每层保留当前最好着法，时间到就返回上一层结果。

**效果**：

- 吃子优先通常能显著提高剪枝率；
- 迭代加深保证“任何时刻都有解”，不会因为深度 5 没搜完而完全没结果；
- 困难档 depth 5 + 8 秒预算。

**缺陷（主动说）**：

- 当前没有把上一层最佳着法排到下一层最前，迭代加深的排序收益没完全兑现；
- 时间检查只在每层之间，单层不可中断。

---

## Q10. 评估函数是什么？将死分数为什么加 depth？

**答**：评估是红正黑负的物质总和：将 100000、车 900、炮 450、马 400、象/士 200、兵 100（过河 200）。

**为什么加 depth**：

```text
MAX 视角：100000 + depth → 更早将死分更高
MIN 视角：-100000 - depth → 更晚被将死分更高（更不坏）
```

这样 AI 不会“能一步杀却绕路”，也不会“必败时随便送”。

**追问：为什么只有物质？**
答：可解释、零依赖、代码量小；代价是没有位置分/机动性/将安全，棋力有限。这是明确的取舍，不是不知道。

---

## Q11. 伪合法着法和安全着法为什么要两种？

**答**：伪合法只按棋子走法规则生成，不检查走完后是否被将；安全着法在伪合法基础上模拟一步，过滤掉送将。

**用途**：

- 搜索用伪合法 + 吃将终局：快，避免每层做全量安全过滤；
- 人类交互、服务端裁决用安全着法：正确，绝不能走出送将。

**追问：既然搜索用伪合法，会不会走出非法棋？**
答：绝大多数情况不会，因为搜索会在下一层吃将并给极低分；但极端被将局面且搜索深度不足时，理论上可能选到未解将着法。改进是根节点先过滤 `getSafeMoves`，搜索内也用合法着法。

---

## Q12. 搜索里“吃将”作为终局，和真正的将死判定有什么区别？

**答**：吃将是“capture-the-king”模型：只要某一层能吃到对方将，就给极大分。真正的将死是“对方被将且没有任何安全着法”。

**差异**：

- 吃将模型在叶节点无法区分将死和困毙；
- 搜索不会主动做“被将时只生成解将着法”；
- 但交互层用 `hasLegalMove` 正确判定将死/困毙，所以对局结果是对的。

**改进**：搜索内用合法着法 + `inCheck`，叶节点判断 `hasLegalMove`；代价是每层多一次安全过滤，可以用“只在被将时过滤”优化。

---

## Q13. 时间预算真的能保证 8 秒返回吗？

**答**：不能严格保证。当前只在每层开始前检查时间，`minimax` 内部没有时钟检查，单层搜索不可中断，最坏会明显超过 8 秒。

**为什么会这样**：同步递归里插入时间检查需要每 N 个节点查一次 `performance.now()`，会有一点开销；当时优先保证代码简单。

**正确改法**：

- 每 1024 个节点检查一次 deadline，超时抛 `SearchAborted`；
- 根节点捕获后返回上一层最佳；
- 放 Web Worker，主线程可随时 `terminate`；
- UI 上显示“思考中”，避免用户以为卡死。

---

## Q14. Pikafish 为什么走 Vite 中间件？生产怎么部署？

**答**：浏览器不能 spawn 本地进程，UCI 又是 stdin/stdout 行协议，所以需要一个本地服务托管。开发期 Vite 已经在跑，用中间件最省一次部署。

**结构**：

```text
浏览器 → POST /__pikafish/analyze
Vite EngineHost → 串行队列 → Pikafish.exe（UCI）
```

**生产**：把 `EngineHost` 抽成独立分析服务，进程池 + 请求队列 + 超时/熔断；前端只依赖分析 API。Vite 中间件只是开发期载体。

**追问：为什么不在 Node 联机服务里？**
答：引擎搜索是 CPU 密集，和 WS 事件循环放一起会互相拖累；独立服务才能单独扩容和限流。

---

## Q15. 串行队列和请求失效怎么实现？

**答**：引擎同一时刻只能搜一个局面，所以所有请求进一个 Promise 队列串行执行；每个请求带递增 `id`，服务端只认最新 `id`。

**三层失效检查**：

1. 进 job 前：`id !== latest` → 直接 stale；
2. `ensure()` 后：引擎启动期间被新请求取代 → stale；
3. `awaitBestmove` 后：搜索期间被取代 → 丢弃结果。

**为什么要 interrupt**：新请求到达时旧搜索可能还在跑，发 `stop` 让旧 job 尽快结束，队列才能推进。

**追问：为什么 `bestmove` 必须消费？**
答：不消费会残留在输出流里，污染下一次请求的解析。

## Q16. 为什么用 `go infinite` + `minDepth`，而不是固定 `movetime`？

**答**：固定时间在简单局面可能浪费，在复杂局面又深度不够。`go infinite` + 轮询主变深度，达到 `minDepth=10` 就停，最晚 4 秒兜底，兼顾质量和延迟。

**实现**：

```text
go infinite
每 40ms 扫 info ... multipv 1 ... depth
depth >= 10 或超过 4s → stop
等 bestmove
```

**代价**：要自己解析 `info`、管理 `stop`；如果引擎不输出 depth，只能等满兜底时间。

---

## Q17. MultiPV 128 是什么坑？

**答**：实测 Pikafish 对超过约 128 的 MultiPV 会静默拒绝并回到默认 1。前端深模式请求 256，如果服务端不钳制，就会只拿到 1 路，推荐走法全丢。

**处理**：

```text
v = min(128, requested)
v = min(v, 当前局面合法着法数)
```

第二层钳制是因为“合法着法可能只有 20 个”，请求 128 没意义，还会让引擎做无效工作。

**面试点**：这是“读引擎真实行为、而不是只看文档”的例子。

## Q18. 胜率条怎么算？为什么不用引擎 WDL？

**答**：用局面分算软胜率：

```text
win  = 100 / (1 + 10^(-s/400))
draw = 60 * exp(-|s|/180)
redWin = win * (100 - draw) / 100
```

`s` 是行棋方视角厘兵。领先一兵约 64%、一马约 88%、一车约 95%。

**为什么不用 WDL**：引擎 WDL 在领先约 300 厘兵后就饱和到 100%，观感差；logistic 永不归 1，和棋概率也有上限，更符合人类直觉。

**视角**：引擎以行棋方为正；玩家执黑时取反。选子指示器不翻转，因为选中的棋子必属行棋方。

## Q19. Elo 和匹配怎么做的？

**答**：标准 Elo，初始 1200，K=32，零和：

```text
E(A) = 1 / (1 + 10^((Rb-Ra)/400))
delta = round(32 * (scoreA - E(A)))
B 的 delta = -A 的 delta
```

匹配：

```text
起始 band ±100
每等 5 秒 +100，上限 ±800
30 秒后无限
双方 band 取 min，避免单方面放宽
选分差最小、等待最久的优先
```

**追问：零和的缺点？**
答：总分守恒但缺少定级赛/K 衰减，新手被高手吃分掉得快；可以加 provisional K=64/32/16。

---

## Q20. 这个项目最大的不足是什么？

**答**：单进程内存状态。房间、队列、对局全在进程里，重启即丢，不能水平扩展。这是演示项目和生产系统的分水岭。

**按优先级**：

1. 单进程内存 → Redis/Postgres + 房间分片；
2. 本地 AI 主线程 → Web Worker + 可中断；
3. 规则简化 → 长将/长捉、自然限着、完整记谱；
4. 引擎只在 dev/preview → 独立分析服务；
5. 安全 → wss、Origin、限流、强制登录。

**为什么先修这个**：它决定系统能不能上线；算法棋力是体验问题，不是可用性问题。

# Part 2 高频追问 40 题（短答）

## 规则与坐标

**Q21. 棋盘怎么表示？为什么二维数组？**
`board[row][col]`，row0 黑底线、row9 红底线，空格 null。走法全是 r/c 偏移，二维可读性高；棋盘小，克隆成本可接受。

**Q22. 马腿怎么判断？**
马走 `(±2,±1)/(±1,±2)`；马腿是长边方向的第一格。例如目标 `(r+2,c+1)` 检查 `(r+1,c)`。8 个方向都要对应正确的腿。

**Q23. 象眼和过河？**
田字中心是象眼，必须在棋盘内且为空；红象 `row>=5`、黑象 `row<=4`，不能过河。

**Q24. 炮架怎么判断？**
炮直线滑动可走空格；吃子时必须恰好隔一个任意棋子（炮架），炮架后第一个子是敌子才可吃。

**Q25. 飞将怎么实现？**
写进“将”的走法：沿同列向上/向下找第一个子，如果是对方将，就可以吃。这样 `isInCheck` 遍历对方将的着法时自然能检测飞将。

**Q26. 三次重复的 key 是什么？**
`10 行棋盘 + "|" + 行棋方`，每格用 `color[0]+type`，空格用 `.`。不含步数/计时，符合“同一局面 + 同一行棋方”。

**Q27. 将死/困毙/重复的判定顺序？**
先判吃将；再判对方无安全着法（被将=将死，未被将=困毙）；最后判新局面第三次出现。顺序影响 reason 准确性。

**Q28. 中文记谱怎么生成？**
棋子名 + 起点线 + 动作 + 终点/步数。横走“平”，纵走“进/退+步数”，斜走“进/退+终点线”。同线两子用前/后，红方行号小为前，黑方行号大为前。

**Q29. 记谱的限制？**
同线 3 个以上同类型棋子时，`idx>=2` 会退回普通写法，可能歧义；标准应使用前/中/后或前/二/三。这是明确的简化。

**Q30. FEN/UCI 怎么转？**
`row0` 对应 FEN 第一行（rank9），红=w、黑=b；UCI `file=a+c`、`rank=9-r`。转换只在 `shared/fen.js`，业务层只用 `{r,c}`。

**Q31. 怎么验证规则正确性？**
三层：协议级冒烟 74 项；规则性质测试（走法对称、不能吃己方、将不能被送）；可补 perft（按深度统计节点数）与标准棋谱回放。

**Q32. 长将/长捉为什么没做？**
它们是“循环裁决”规则，需要记录连续将军/捉子意图和同一局面序列，复杂度高；当前三次重复直接判和，是明确简化。

## 搜索算法

**Q33. Minimax 和 negamax 的关系？**
数学等价。negamax 每层返回 `-search(-beta,-alpha)`，代码短，但要求评估对称；minimax 的 max/min 更好解释，也不容易在红黑视角上出错。

**Q34. Alpha-Beta 的正确性怎么保证？**
只要窗口传递正确，剪枝只去掉“不可能被上层选中”的分支；根节点用 `(-∞,+∞)` 全窗口，最终值等于 Minimax。

**Q35. 复杂度到底多少？**
纯 Minimax `O(b^d)`，b≈40、d=5 → 约 1.02 亿叶子；Alpha-Beta 理想 `O(b^(d/2))` → 约 2 万；实际取决于排序，介于两者之间。

**Q36. 为什么叶子节点还要生成走法？**
代码先 `getAllLegalMoves`，再判断 `depth===0`，所以叶节点也生成。好处是能发现“无着法”终局；坏处是浪费。优化是把 depth 判断提前，只在需要终局时生成。

**Q37. 地平线效应是什么？**
搜索到固定深度刚好停在吃子交换中途，评估把“暂时少一个子”当成永久劣势。解决：静止搜索（只扩展吃子/将军）、延拓、更好的评估。

**Q38. 置换表怎么做？**
Zobrist 哈希（每格每子随机数 XOR，再 XOR 行棋方）→ 表项存 `depth/score/flag/bestMove`。注意“分数依赖深度”，不同深度要用不同 bound 或只存足够深的。

**Q39. 为什么 AI 会卡 UI？怎么改？**
Minimax 是同步递归，跑在主线程；depth 5 可能几秒，期间 React 无法渲染。改 Web Worker：主线程发 FEN/局面，Worker 搜索，支持 abort；主线程只收结果。

**Q40. 黑方 AI 的评估方向怎么保证？**
评估函数固定红正黑负；根节点 `isMaximizing = aiColor === 'red'`。这样执黑时 AI 最小化红方分，等价于最大化自己。

**Q41. 提升棋力的优先级？**
1) 搜索合法化/将死正确；2) 位置分 + 将安全；3) 静止搜索；4) 置换表；5) 更好排序（MVV-LVA/killer/history）；6) 开局库。

## Pikafish

**Q42. UCI 握手流程？**
`uci → uciok`；`setoption Threads/Hash/ShowWDL`；`isready → readyok`；`position fen ...`；`go`；读 `info`；`bestmove`。

**Q43. 引擎崩溃怎么恢复？**
当前 job catch → `dispose()`（quit/kill）；下一次请求 `ensure()` 重新 spawn + 握手。HTTP 返回 `ok:false`，前端提示。

**Q44. 为什么不用 WASM？**
`public/pikafish` 有历史 WASM 资产但未接入；原生 exe 的棋力/线程/NNUE 更完整。WASM 适合纯静态部署，但要处理线程/内存/体积，当前不是优先项。

**Q45. 分析请求怎么防抖和去重？**
`EngineController` 用 `_activeFen` 去重、`_seq` 防过期、`AbortController` 中止上一个、开局结果缓存；服务端用 `latest id` 再兜一层。

**Q46. 为什么前端也要 `seq`，服务端也有 `id`？**
前端 `seq` 防“旧响应覆盖新状态”；服务端 `id` 防“旧搜索占用引擎”。两层解决不同问题，不能省。

**Q47. `MultiPV` 结果怎么解析？**
每个 `multipv` 取 depth 最大的一条；`best=multipv 1` 作为全局分数；保留 `score cp/mate`、`wdl`、`pv`、`depth`。

**Q48. 深模式和浅模式的差异？**
深：MultiPV 256（钳 128）、infinite、minDepth 10、4 秒兜底，用于选子推荐/热力；浅：MultiPV 5、500ms，用于胜率条。深结果可降级给浅，反之不行。

## 联机

**Q49. 为什么 WebSocket，不用 HTTP 轮询？**
对手走子、离线、匹配、结算都是服务端主动推送；轮询延迟高且浪费。WebSocket 全双工、低开销。

**Q50. 为什么不用 socket.io？**
协议简单、消息类型少；心跳/重连/会话恢复都要业务控制，库的默认行为反而要覆盖；少一个依赖，协议可逐行解释。

**Q51. 房间和对局的状态机？**
`waiting → playing → over`；连接维度 `online ↔ offline(宽限)`。两个维度正交：playing 时允许一个座位 offline，对局不暂停。

**Q52. `applyMove` 校验哪些？**
状态 playing、轮到该玩家、`baseSeq===seq`、起点有己方子、终点在 `getSafeMoves` 内；任何失败都不改状态。

**Q53. 双发/重试会不会重复落子？**
不会。成功后 `seq+1`，重试带旧 `baseSeq` 会被 `stale_seq` 拒绝；这是“至多一次”的效果。

**Q54. 消息顺序有问题吗？**
排位结算 `rating.update` 在 `endGame` 内同步触发，可能先于 `game.over` 到达。客户端把它当独立面板数据，所以没 bug；更严谨是并入快照或放到 `game.over` 后。

**Q55. 房间怎么回收？**
`done = over || playerCount==0`，且所有座位离线时 `reap` 删除 `games/rooms`；结束但有连接则保留到关闭后的宽限期。

**Q56. 单进程怎么扩展？**
WS 网关无状态；房间状态进 Redis；按 roomId 分片/sticky；广播走 Pub/Sub；排位/账号进 Postgres；`seq` 用 Lua/事务原子递增。

**Q57. 安全上还缺什么？**
wss、Origin 白名单、限流、登录失败锁定、消息大小限制、游客身份不可信、`sync.request` 未校验成员。

**Q58. 为什么 JSON 落盘？一致性？**
零依赖、可读、克隆即跑；`writeFileSync` 不是事务，崩溃可能写坏。生产应原子写（临时文件+rename）或数据库。

## 重连

**Q59. 为什么用 sessionStorage 不用 localStorage？**
localStorage 多标签共享，容易两个标签抢同一座位；sessionStorage 按标签隔离，刷新保留、关标签清空，符合“一个标签一局”。

**Q60. 退避和服务端宽限期怎么配合？**
退避 1/2/4/8/16 秒，最多 8 次；前 5 次覆盖 30 秒宽限期。超过宽限期服务端判负，客户端即使连上也看到 `over`。

**Q61. 旧连接残留怎么处理？**
`room.resume` 时如果 `player.ws` 存在且不是新连接，先 `close()`；旧连接的 close 事件里 `findGameBySocket` 已找不到它，不会误判离线。

**Q62. 宽限期 30 秒合理吗？**
是折中：覆盖刷新/短暂断网，又不给恶意拖时间太多。竞技产品可以 60-120 秒 + 可暂停；休闲可以 15 秒。

**Q63. 刷新后怎么恢复动画所需信息？**
快照只给最终棋盘；客户端用 `prevBoard` 与新棋盘做差，重建 `from/to/captured`，再触发同一套动画。

## 前端

**Q64. 为什么不用 Redux？**
状态集中在一个对局域，跨组件共享少；Redux 的 action/selector 样板不划算。真正问题是 hook 长，下一步用 `useReducer` 拆转移。

**Q65. 悔棋为什么用快照？**
走法受吃子/将军影响，反向推演容易错；快照回滚必然正确，内存成本是每步一个 90 格引用数组，可接受。

**Q66. AI 异步竞态怎么防？**
`aiRef` 防重入；App effect key 防重复触发；`versionRef` 在 reset/undo/replay 时递增，AI 返回后发现版本变了就丢弃。

**Q67. 棋盘为什么要实测几何？**
棋盘由 CSS 变量 + `transform: scale()` 控制；写死常量会在缩放/不同屏幕错位。实测 `(0,0)/(0,1)/(1,0)/(5,0)` 求 cell/step/river，再除以 scale。

**Q68. Canvas 怎么处理 DPR？**
`canvas.width = cssW * dpr`，`ctx.setTransform(dpr,0,0,dpr,0,0)`；绘制用 CSS 坐标，高清屏不糊。

**Q69. 热力图为什么用相对排名？**
绝对分归一化会让优势方全红、劣势方全蓝；组内相对排名只让最强/最弱拿极值色，中间自然变淡。

**Q70. 白屏事故根因？**
某模块的 duck-typing re-export 指向 `undefined`，订阅 effect 抛错，React 19 卸载整棵树。修复：直接 import；分析管线 try/catch；`analyzeOnLoad` 幂等。

**Q71. PWA 离线能做什么？**
能打开外壳、单机对弈；联机和 Pikafish 分析需要网络/本地服务。SW 四类策略：导航网络优先、引擎资源缓存优先、静态 stale-while-revalidate、非 GET/跨域不接管。

**Q72. 为什么 SW 只在生产注册？**
开发态会拦截 Vite 模块和 HMR，导致热更新失效；所以用 `import.meta.env.PROD` 控制，PWA 验证必须 build+preview。

## 工程与排查

**Q73. 联机怎么测试？**
4 个协议级冒烟脚本，直接开多个 WebSocket 发真实消息，断言响应与状态，共 74 项；P1/P4 自建隔离端口，P2 用短宽限期。

**Q74. 如果线上双方棋盘不一致，怎么排查？**
先查 `seq` 是否一致 → 查是否有人收到 `stale_seq` 未 `sync` → 查服务端快照与客户端 `applySnapshot` 的 diff → 查是否有旧连接双写 → 最后查 `getSafeMoves` 版本是否一致。

**Q75. 如果 AI 走了非法棋，怎么定位？**
复现局面 → 打印 `getAllLegalMoves` 结果 → 检查是否是“伪合法未解将” → 检查根节点是否过滤安全着法 → 检查 `triggerAIMove` 的 `versionRef` 是否让旧结果落盘。

**Q76. 引擎总是超时怎么排查？**
查 exe 路径/权限 → 查 `uciok/readyok` 是否返回 → 查是否残留 `bestmove` 污染 → 查 MultiPV 是否超 128 → 查 `minDepth` 是否永远达不到 → 查是否有旧 job 未 stop。

**Q77. 项目最大的技术债？**
单进程内存状态；其次是主线程 AI 和简化规则。按“可用性 > 正确性 > 体验”排序修。

# Part 4 白板题应对（可能会让你现场写）

## 4.1 写“马”的走法生成

```js
const KNIGHT = [
  [-2, -1, -1, 0], [-2, 1, -1, 0],
  [-1, -2, 0, -1], [1, -2, 0, -1],
  [2, -1, 1, 0], [2, 1, 1, 0],
  [-1, 2, 0, 1], [1, 2, 0, 1],
];
for (const [dr, dc, lr, lc] of KNIGHT) {
  const r = row + dr, c = col + dc;
  if (!inBounds(r, c)) continue;
  if (board[row + lr][col + lc]) continue; // 马腿
  if (board[r][c]?.color === color) continue;
  add(r, c);
}
```

讲解点：腿是“长边方向第一格”，不是目标格；8 个方向都要单独列。

## 4.2 写 Alpha-Beta

```js
function ab(board, depth, alpha, beta, max) {
  if (depth === 0) return evaluate(board);
  const moves = gen(board, max ? 'red' : 'black');
  if (!moves.length) return max ? -MATE : MATE;
  let best = max ? -Infinity : Infinity;
  for (const m of order(moves)) {
    const score = ab(apply(board, m), depth - 1, alpha, beta, !max);
    if (max) {
      best = Math.max(best, score);
      alpha = Math.max(alpha, best);
    } else {
      best = Math.min(best, score);
      beta = Math.min(beta, best);
    }
    if (beta <= alpha) break;
  }
  return best;
}
```

讲解点：先写清 max/min 与 alpha/beta 的更新，再提“根节点要保留 move”。

const expected = (a, b) => 1 / (1 + 10 ** ((b - a) / 400));
const delta = Math.round(32 * (scoreA - expected(ra, rb)));

讲解点：零和、四舍五入、K 的选择。
